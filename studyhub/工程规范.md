## 二、修改工作流（十一步，一步都不能跳）

每次修改按顺序走完；任何一步失败，修完从头重跑。

1. **建分支** — 从 main 开修改分支：`git checkout -b <类型>/<简短英文名>`（如 `fix/frac-stack`、`feat/pen-page`）。**禁止直接在 main 上改代码**（2026-10-29 起，详见第八节）。
2. **改代码** — 编辑 `resources/index.html`。
3. **语法自查** — 如果改了数据/正则，先用 `node -e "..."` 单独验证正则能编译（教训：`(?=...)` 误写成 `++` 报 "Nothing to repeat"；字符类里放分组直接报错）。
4. **格式审查** — 仓库根目录执行：
   ```
   node tools/sweep.js    → 必须 0 问题（当前基线：689 段）
   node tools/audit.js    → 必须 0 处
   ```
5. **端到端测试** — `node tools/test-app.js` → 必须 **7/7 通过**。改了存储/画笔/分页逻辑后尤其必须跑。
6. **关掉正在运行的应用** — `taskkill /F /IM StudyHub-win_x64.exe`（exe 运行时被锁，不杀掉构建必失败）。
7. **构建** — 仓库根目录 `bin\neu.cmd build --release`。产物在 `dist\StudyHub\StudyHub-win_x64\`。
8. **真机启动验证** — 双击/启动 exe，确认：① 能打开；② 之前画的笔迹和补充还在；③ 新改动生效。**这一步就是"验收"：不正确就在分支上继续修，修不好就按第八节回滚整条分支。**
9. **同步浏览器副本** — 把 `resources\index.html` 复制覆盖 `C:\Users\hjh\Desktop\learninglist\index.html`。
10. **提交合并推送** — 验收通过后才允许 commit（格式见第八节）→ 切回 main 合并分支 → `git push StudyHub main`。
11. **记忆备份** — 把 workspace 记忆目录同步到 `D:\WorkBuddyMemory备份\`。

## 三、数学内容格式规范（写进 COURSE_DATA / CONCEPT_DETAILS 的文本）

1. **上标下标**：源码里写平铺记号，由 mathify 渲染：
   - 上标 `x^2`、`e^{1/x}`；下标 `x0`→x₀、`a_n`→aₙ 风格。
   - **禁止中文出现在 `^{}` 或 `_{}` 里面**（教训：渲染出乱码堆）。
   - **禁止手写 HTML `<sub>/<sup>` 与记号混用造成嵌套**，统一用记号。
2. **分式**：**所有除法一律写成 `a/b` 形式**，mathify 会自动堆叠成分式（用户明确要求，见斜杠即堆叠）。允许：
   - 整组括号 `(f(x)/g(x))`、裸组 `f(x)/g(x)`、简单比 `1/2`、混合 `√2/2`，外层括号自动剥离。
3. **极限**：`lim` **必须带下标**（`lim_{n→∞}`、`lim_{x→x0}`），不允许裸 lim（教训：用户截图质问"lim下面怎么没有x趋向于多少"）。
4. **字体约定**：字母斜体、数字正体、函数名（sin/cos/lim/max）正体。mathify 自动处理，不要手工加 `<i>`。
5. **允许的 Unicode 数学字符**（白名单外新增字符要先确认 mathify 的 run 检测不会把它截断）：
   `− Δ □ ⁺ ² ³ ¹ ± ∞ √ π ′ · ×`、希腊字母 `Α-ω`。
6. **全局替换警示**：做全局文本替换前，先检查会不会破坏 JS 源码本身（教训：把 `x00` 全局换成 `x₀0` 时毁掉了 `"\x00"` 转义序列，改回来花了好几轮）。
7. 每个知识点应有 📖 详解（CONCEPT_DETAILS）；重复标题的概念允许暂缺，但新增概念必须带。

## 四、渲染引擎（mathify）修改规范

mathify = 公式排版引擎，改它属于**高危操作**：

1. 改动前先读懂三件事：
   - **非 CJK run 检测**：连续的非中文字符段才进入排版，中文不清(char-by-char 处理是禁区)。
   - **元素对占位保护**：`<sub>...</sub>`、`<sup>...</sup>`、`<mark>` 等整个元素替换成 `\x00数字\x00` 占位符，排版完再还原——**任何新逻辑必须先过占位符再排版**（教训：只保护单个标签导致分式引擎吃掉下标内容，渲染出 "1 1" 垃圾）。
   - **分式引擎 5 种模式**：`(a/b)` 整组 / GRP/GRP / SIMP/GRP / GRP/SIMP / SIMP/SIMP，SIMP 含占位符、数字、上标 Unicode、`!±∞√π`、希腊字母、`′·×`。
2. 改完必须 `node tools/sweep.js` 全过，再人眼抽查极限、分式、上下标混合的段落。
3. **分页/内容变动后必须触发 `sizeCanvas()`**（教训：翻页后画布位图是旧的，笔迹错位）。`refreshLesson()` 已在结尾调用，新增任何改变页面内容的入口都要跟上。
4. 分页权重 `PAGE_WEIGHT = 2.6` 是调过的平衡值，除非用户要求，不要动。

## 五、存储与持久化规范（红线区）

用户的字迹和补充是**不可再生的数据**，此区规则最严格：

1. **磁盘为主，localStorage 为缓存**：
   - 主存储：`%APPDATA%\Roaming\StudyHub\data.json`（`Neutralino.filesystem.writeFile` 400ms 防抖落盘）。
   - 启动时 **并集合并（union merge）**：磁盘 ∪ localStorage 逐 key 取存在者，**绝不允许整体覆盖**（教训：双实例 UDF 冲突直接清空了用户全部笔迹）。
2. **单实例锁**：`.lock` 文件 + 20 秒心跳，锁超过 60 秒视为陈旧；发现活锁时**等 10 秒后接管**，不是直接退出（教训：测试实例持锁导致应用"打不开"，静默退出）。
3. **按页存储**：笔迹和补充的 key 必须带页号：`<课id>#p<页号>`（如 `c-gaoshu/gds-p11#p0`）。旧的无页号数据靠 `migrateAll()` 迁移——**改 key 结构必须写迁移**，不允许留下读不到的旧数据。
4. Neutralino v6.10 fs API 是**位置参数**：`writeFile(filename, data)`、`readFile(filename)` 返回字符串；**不是** v4 的 `{path, data}` 对象签名。`createDirectory(path)` 在目录已存在时会抛异常，要先 try/catch。
5. WebView2 用户数据目录按 exe 名做键（`%APPDATA%\Roaming\StudyHub-win_x64.exe`），重新构建不会丢 localStorage；但**不要依赖它**，一切以磁盘 data.json 为准。
6. 排查存储问题先看 `%APPDATA%\Roaming\StudyHub-init.log`（启动日志，含重试记录）。
7. 改存储代码后，除了 e2e 7/7，还要真机验证：画几笔 → 完全退出 → 重开 → 笔迹还在。

## 六、Neutralino 构建陷阱速查

| 陷阱 | 对策 |
|---|---|
| exe 运行时被锁，构建报无法写入 | 构建前 `taskkill /F /IM StudyHub-win_x64.exe` |
| `neu build` 慢或卡 | 确认在仓库根目录执行 `bin\neu.cmd build --release` |
| 改了 index.html 但应用没变化 | 确认改的是 `resources\` 下的文件，且重新构建了（不是直接改 dist） |
| 应用双开导致数据丢失 | 单实例锁已内置；测试时不要同时开两个实例 |
| 沙箱里 git push 被 SIGTERM | 推送时需关闭沙箱执行 |

## 七、QA 关卡（交付标准）

交付前四关全过才算完成：

1. `node tools/sweep.js` → **0 问题**
2. `node tools/audit.js` → **0 处**
3. `node tools/test-app.js` → **7/7 通过**
4. 真机启动 → 能打开、数据在、新功能生效

修 bug 时用**真实运行 + 真实数据**验证，不靠口头分析（用户惯例：多轮测试 + 前后对比）。

## 八、Git 分支与提交规范（2026-10-29 起）

**分支工作流**：每次修改必须建分支，验收通过才合并进 main。main 永远是"能用的稳定版"。

1. 开工先建分支：`git checkout -b <类型>/<简短英文名>`（分支名用英文短横线，如 `fix/frac-stack`）。
2. 在分支上改代码、跑 QA 四关（第七节），构建 + 真机验收。
3. **验收失败且修不好 → 回滚**：`git checkout main && git branch -D <分支名>`。工作区自动恢复原状，main 毫发无损——这就是分支的好处。
4. **验收通过 → 才允许 commit**，然后合并：`git checkout main && git merge <分支名>`。
5. 合并后删除分支：`git branch -d <分支名>`；推远程：`git push StudyHub main`（远程名是 **StudyHub**，不是 origin）。
6. 已经合并进 main 之后才发现问题：用 `git revert <提交号>` 生成反向提交修复，**禁止 force push**。

**提交信息格式**：`<类型>/<具体改了什么>`

- 类型取这四个：`feat`（新功能）/ `fixbug`（修 bug）/ `docs`（文档）/ `refactor`（重构）
- 描述必须一句话说清**具体改动**，让别人（和三天后的自己）不用点开就知道改了啥：
  - ✅ `fixbug/修复下标被误渲染成斜体`
  - ✅ `feat/分式引擎支持方括号组堆叠`
  - ✅ `docs/工程规范加入分支工作流`
  - ❌ `修改`、`update`、`修复bug`（没说清改了什么，不合格）
- **一次提交只做一件事**；修数据丢失这类大问题，commit message 里写清根因。
- dist 产物跟着源码一起提交（当前约定），构建后记得 `git add dist`；dist 产物冲突时先 `git checkout -- dist` 再处理。

## 九、红线清单（绝对禁止）

1. ❌ 禁止任何形式的"整体覆盖"用户数据（只能并集合并）。
2. ❌ 禁止在存储代码未过 e2e + 真机持久化验证前宣布完成。
3. ❌ 禁止把中文写进 `^{}` / `_{}`，禁止裸 `lim`，禁止用 `/` 之外的写法表达除法后不堆叠。
4. ❌ 禁止全局替换前不检查 JS 源码影响面。
5. ❌ 禁止跳过 taskkill 直接构建。
6. ❌ 禁止改完只测桌面端不测浏览器副本（或反之）——两份都要能用。
7. ❌ 禁止删除 tools/ 下的 QA 工具或跳过 QA 关卡交付。
8. ❌ 禁止直接在 main 上改代码（必须建分支）；禁止验收不通过就 commit。
